# Accounts architecture

Accounts owns the immutable asset catalogue, ordinary user wallets, internal non-login issuance accounts, own-wallet projection, exact peer lookup and controlled demo issuance. Implementation lives in `apps/api/src/modules/accounts/`; `accounts.service.ts` owns persistence and `accounts.controller.ts` exposes authenticated GET `/api/accounts` and `/api/peers?handle=...`. The module imports Auth's narrow identity adapter and Ledger's session-required writer. Transfers alone coordinates user settlement. There are no public balance mutation or issuance endpoints.

`accounts.models.ts` defines AssetRecord, AccountRecord and IssuanceRecord. `schema.ts` initializes strict validators and rejects incompatible pre-existing data; initialization creates named indexes before serving. Assets have unique code and precision 0..8. Accounts have exactly one owner: userId or systemKey `demo-issuance`, each uniquely indexed with assetId using partial indexes. Balances are signed BSON Long, always read without promotion. User balances are nonnegative; issuance system balances are nonpositive. `quantity.ts` converts decimal strings through bigint and refuses overflow, nonpositive quantities, unsafe JSON numbers and excess precision. API formatting preserves every base unit.

Reading a missing account projects zero and never writes. Peer lookup is exact normalized ASCII public handle and exposes only ID/handle/name for active users. Caller identity comes from AuthGuard; unknown query fields are refused. HTTP reads are no-store. Persisted fixed-window limits use hashed caller/action keys and TTL cleanup, 240 reads or 120 peer lookups per minute. Expiry is bucket selection, not TTL timing.

`createAsset` atomically inserts the catalogue, legacy chain head and custody head. New assets have a stable unique identity key, SIMULATED/DEMO_CRYPTO metadata, revision and custody enabled. Identical reruns return the original asset and incompatible metadata fails. `setAssetStatus` changes catalogue/head and increments the asset revision in one transaction. Asset identity and precision have no mutation API. `ensureUser` requires ClientSession and provisions zero atomically under the unique owner/asset index; custody-enabled operations require matching durable wallet linkage. Transfer debit and credit require active account status and explicit bounds; supported account suspension writes that same account record.

For custody-enabled assets, issuance also fences the active application wallet and creates a root lot in the same transaction. Transfers fence both wallets and write lineage alongside the journal, chain and outbox. Legacy assets are not silently upgraded. Missing provenance/linkage prevents settlement rather than manufacturing roots. See [wallets](WALLETS.md) and [custody](CUSTODY.md) for v2 APIs, compatibility and migration prerequisites. UI asset administration and supply policy remain pending.

`issueDemo` is a trusted internal function called by an explicit CLI after `demo-target.ts` checks development/test, exact loopback URI and approved database name. No configuration or startup grants balances. The CLI's synthetic users have `.invalid` emails and an explicitly supplied password; sessions created while provisioning are revoked. Issuance uses a stable fixture key, active-user revision and head eligibility writes, signed system debit, bounded user credit and balanced `demoIssuance` journal in one 10-second snapshot/majority transaction. Reruns compare recipient/asset/units before returning; conflicting keys fail without effects. Negative system capacity is finite.

See [LLD](WALLET_AND_TRANSFER_LLD.md) for exact types, APIs and decisions and [QA map](WALLET_AND_TRANSFER_QA.md) W01-W11/T04-T07 for acceptance. Tests: `tests/unit/quantity.test.mts`, `accounts.test.mts`, `demo-fixtures.test.mts`, `tests/features/wallet.feature`, `transfers.feature` and `tests/steps/transfer.steps.mts`. Commands: `scripts/npm.ps1 run test:unit`, `test:functional`, `check`; functional tests require local replica set and disposable databases. Recorded automated verification and remaining limits are in the QA map. Production issuance, catalogue administration UI, pagination and performance validation remain out of scope.
