# Transfer recovery and outbox architecture

`apps/api/src/workers/transfer-recovery.service.ts` defines TransferRecoveryService, registered by TransfersModule. Nest's onApplicationBootstrap starts a 2-second timer only after all collection initialization. One tick per process may run; each scans up to 20 due PENDING requests and calls the same TransfersService executor used by HTTP. `stop()` clears the timer and drains in-flight work; onModuleDestroy calls it. Tests explicitly stop automatic ticking and use deterministic calls. Multiple processes are safe because admission identity, attempt-token fencing, conditional status writes and unique artifacts enforce correctness, not the timer.

Claims last 30 seconds; transactions have a 10-second timeout. Recovery respects nextAttemptAt and expired/null leases, increments attempts, and uses fresh UUID tokens. Infrastructure errors leave requests PENDING with exponential delay capped at 60 seconds plus up to 499 ms jitter. There is no retry-count rejection. Unknown commit outcomes are reconciled through the same durable ID and never converted into business rejection. Session logout after admission is not cancellation. Stale executors cannot overwrite a newer token or terminal result. Safe warning logs contain no payloads or credentials.

`outbox.service.ts` defines OutboxModule/OutboxService. `committed(transfer,at,session)` inserts one schema-version-1 `transfer.updated` event with stable `transfer:<id>:committed` eventId, transfer/participant IDs, COMMITTED status and UTC timestamp. Collection validation requires this shape; unique eventId and delivery-scan indexes exist. It shares the financial transaction. deliveredAt stays null and no event is deleted or falsely marked delivered: socket transport is future work. Event IDs provide a deduplication boundary for eventual at-least-once delivery.

Configuration is fixed bounded constants in this release, with existing database/environment configuration only. No standalone worker command or deployment is required; every API instance owns a recovery loop. Future deployment may separate the worker without introducing another executor. Pending age and backlog are queryable persisted state; external alerting/load validation are future operational work.

Test locations: `tests/unit/transfer-recovery.test.mts`, `tests/features/transfer-recovery.feature` and transfer harness/steps. `scripts/npm.ps1 run check` runs both required suites and produces XML/HTML reports; actual verification and limits are recorded in the QA map. Injected rollback/response-loss boundaries are distinct from real network failover or process-kill evidence and must be reported separately.
