# Transfer recovery and outbox architecture

`apps/api/src/workers/transfer-recovery.service.ts` defines TransferRecoveryService, registered by TransfersModule. Nest's onApplicationBootstrap starts a 2-second timer only after all collection initialization. One tick per process may run; each scans up to 20 due PENDING requests and calls the same TransfersService executor used by HTTP. `stop()` clears the timer and drains in-flight work; onModuleDestroy calls it. Tests explicitly stop automatic ticking and use deterministic calls. Multiple processes are safe because admission identity, attempt-token fencing, conditional status writes and unique artifacts enforce correctness, not the timer.

Claims last 30 seconds; transactions have a 10-second timeout. Recovery respects nextAttemptAt and expired/null leases, increments attempts, and uses fresh UUID tokens. Infrastructure errors leave requests PENDING with exponential delay capped at 60 seconds plus up to 499 ms jitter. There is no retry-count rejection. Unknown commit outcomes are reconciled through the same durable ID and never converted into business rejection. Session logout after admission is not cancellation. Stale executors cannot overwrite a newer token or terminal result. Safe warning logs contain no payloads or credentials.

`outbox.service.ts` defines OutboxModule/OutboxService. `committed(transfer,at,session)` inserts one schema-version-1 `transfer.updated` event with stable `transfer:<id>:committed` eventId, participant IDs, COMMITTED status and UTC timestamp in the financial transaction. Operations now delivers eligible events to durable participant inboxes. Both inbox upserts and `deliveredAt` acknowledgment commit together; duplicate events retain one notification per recipient. The persistent activation boundary leaves older events retained and reported separately. Socket delivery remains future work. See [notification leases, jobs and operations](DEMO_ENHANCEMENTS.md#notifications-and-verification-jobs).

Transfer recovery scheduling remains bounded constants. Supported product admission/review/read policies use authoritative [configuration readers](DEMO_ENHANCEMENTS.md#supported-configuration); they do not rewrite admitted outcomes. Each API instance owns recovery and Operations loops, with shutdown draining and claim fencing. Operations adds a 30-second delivery lease and a 120-second verification-job lease. Read-only jobs enforce record budgets inside their separate ledger/chain/custody snapshots; they never repair balances or historical evidence. External alerting/load validation remains future operating work.

See [LLD](WALLET_AND_TRANSFER_LLD.md), [QA map](WALLET_AND_TRANSFER_QA.md) R01-R08/C04. Test locations: `tests/unit/transfer-recovery.test.mts`, `tests/features/transfer-recovery.feature` and transfer harness/steps. `scripts/npm.ps1 run check` runs both required suites and produces XML/HTML reports; actual verification and limits are recorded in the QA map. Injected rollback/response-loss boundaries are distinct from real network failover or process-kill evidence and must be reported separately.
