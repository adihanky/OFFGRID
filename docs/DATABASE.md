# Database lifecycle and transaction integration

`apps/api/src/database/database.module.ts` globally exports `DatabaseService`, the sole application MongoClient owner. `database.service.ts` constructs the official driver using validated environment settings, connects in `onModuleInit`, exposes the configured database, and closes in `onApplicationShutdown`. No schema or financial record belongs to this module; Auth, Accounts, Transfers, Ledger, Chain and Outbox initialize their own collections and indexes before traffic starts.

The connection closes after every module's `onModuleDestroy` hook. This ordering lets TransferRecoveryService stop its timer and drain its current executor before shared database access disappears. Nest application shutdown must be awaited. A force-killed process relies on durable requests, finite leases and later recovery; orderly shutdown is not a replacement for recovery.

All multi-document settlement and issuance operations obtain a ClientSession from this client. Coordinators own transactions and pass the same session explicitly to every sequential mutation; submodules do not open nested write transactions. Domain transactions use snapshot reads, majority writes and primary reads with a bounded timeout. New registration atomically provisions a user and wallet. Custody-enabled assets include wallet fences and lot/event/edge/head writes in the financial transaction. The standalone [migration assessment](WALLETS.md) opens a read-only snapshot without initializing application collections or starting workers. See [Wallet and Transfer LLD](WALLET_AND_TRANSFER_LLD.md) for the state machine and driver policy.

Existing configuration is `MONGODB_URI`, `MONGODB_DB` and `MONGODB_REPLICA_SET`. The pool limit is 10 and initial selection/connect deadlines are 3 seconds. `readiness()` runs bounded `hello` and requires the configured replica set, writable primary and numeric logical-session support. It returns sanitized status fields and no connection details. Startup initialization failures prevent HTTP readiness. Production credentials, backups and redundancy remain deployment responsibilities.

Verification: existing health unit/Cucumber suites exercise readiness through controlled responses; wallet/transfer Cucumber tests use isolated real replica-set databases. `tests/unit/database-lifecycle.test.mts` verifies that in-flight recovery completes before the real DatabaseService shutdown hook closes its mocked connection. `scripts/db.ps1 verify` exercises actual commit/rollback in a temporary collection. Run `scripts/npm.ps1 run check` and inspect both JUnit reports; final execution evidence lives in [onboarding](../onboarding.md) and the [QA map](WALLET_AND_TRANSFER_QA.md).
